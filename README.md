# kmg-doc

KMG フレームワーク全体の設計方針およびドキュメントを管理するプロジェクトである。

KMG フレームワークは、共通基盤となる **`kmg-*`** ディレクトリと、それを利用してアプリケーションを構築する **`kb-*`**、**`mk-*`**、**`gr-*`** ディレクトリで構成される。加えて、特別用途として **`ku-*`**、**`sn-*`** ディレクトリを持つ。

---

## プロジェクト構成

```text
KMG Framework
│
├─ kmg-*      フレームワーク・共通基盤
│
├─ kb-*       ドキュメント・共通ライブラリ・インフラ・ツール
│
├─ mk-*       フロントエンドアプリケーション
│
├─ gr-*       バックエンドアプリケーション
│
├─ ku-*       他リポジトリ（プロジェクト）のコピー利用（特別用途）
│
└─ sn-*       プロトタイプ版（特別用途）
```

`kb`、`mk`、`gr`、`ku`、`sn` のプロジェクト（リポジトリ）は、`kb001`、`mk001` のように番号で連番とする。

---

## kmg

KMG フレームワーク全体で利用する共通基盤プロジェクト群である。

フレームワークそのものや開発ツールなど、アプリケーションに依存しない機能を提供する。

主なプロジェクト

| プロジェクト | 説明 |
| --- | --- |
| `kmg-core` | KMG シリーズの中核となる共通ライブラリ |
| `kmg-fund` | Spring Boot をベースとした基盤機能 |
| `kmg-tool-base` | Java 開発および KMG シリーズ共通ツール |
| `kmg-tool-cli` | コマンドラインツール |
| `kmg-tool-gui` | GUI ツール |
| `kmg-javafx` | JavaFX 共通機能 |
| `kmg-jrnl` | KMG シリーズの記録・管理 |

---

## kb

ドキュメント、共通ライブラリ、インフラストラクチャ及びツールを提供するプロジェクト群である。

役割ごとにライブラリを分割し、再利用性を高める。

プロジェクト例

* `kb-todo-core`
* `kb-todo-security`
* `kb-todo-cache`
* `kb-todo-logging`
* `kb-todo-test`

`kb-todo-common` のような責務の曖昧なライブラリは作成せず、役割ごとに分割することを基本方針とする。

---

## mk

フロントエンドアプリケーションプロジェクト群である。

採用技術例

* TypeScript
* React
* Next.js

役割例

* Web UI
* API 通信
* 認証画面
* クライアントサイド処理

プロジェクト例

* `mk-todo-main-web`
* `mk-todo-admin-web`
* `mk-todo-member-web`

---

## gr

バックエンドアプリケーションプロジェクト群である。

採用技術例

* Java
* Spring Boot

主なレイヤー

* Presentation
* Application
* Domain
* Infrastructure
* Repository

REST API と業務ロジックとDBを実装する。

プロジェクト例

* `gr-todo-main-api`
* `gr-todo-member-api`
* `gr-todo-auth-api`
* `gr-todo-db-api`

---

## ku

他のリポジトリ（プロジェクト）をコピーして利用するための特別用途プロジェクト群である。

既存の `kb-*`、`mk-*`、`gr-*` とは役割が異なり、外部プロジェクトを取り込み・流用する際に用いる。

---

## sn

プロトタイプ版のための特別用途プロジェクト群である。

本番向けの `kb-*`、`mk-*`、`gr-*` とは区別し、試作・検証を目的としたプロジェクトに用いる。

---

## 依存関係

KMG フレームワークを利用するプロジェクトの依存関係は、次の一方向とする。

```text
mk-*  →  gr-*  →  kb-*
          ↑
        kmg-*
```

* `kmg-*` はフレームワーク・共通基盤を提供する。
* `kb-*` はドキュメント、共通ライブラリ、インフラおよびツールを担当する。
* `mk-*` はフロントエンドを担当する。
* `gr-*` は業務ロジック、DBおよび API を担当する。
* `ku-*` は他リポジトリのコピー利用のための特別用途である。
* `sn-*` はプロトタイプ版のための特別用途である。
* 逆方向の依存は作成しない。

---

## 設計方針

* 責務ごとにプロジェクトを分割する。
* フレームワークとアプリケーションを明確に分離する。
* 共通ライブラリは役割ごとに分割する。
* 一方向の依存関係を維持する。
* 保守性・再利用性・拡張性を重視した設計とする。
